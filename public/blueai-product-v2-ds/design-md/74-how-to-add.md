## 74 How to add a feature

**Status:** Meta (no parts).

**Why:** The system only pays off if the next feature is built from it. These are the steps from a new task to a screen merged into V2.

### From a new task to a screen in V2

1. **Name the job it serves.** One line: which of the three jobs in section 01 it serves, and which principle in section 02 it leans on. If it serves none, question the feature before designing it.
   - If the feature shows money or cash out (a payout, a balance, an earnings figure), read the money rule in section 01 and decision D3 first (`design-md/01-concept.md:21, 47`; section 73). Until D3 is decided, show days, not dollars, beyond the $10 cash-out minimum. Cash out lives on the site, never in the app: link to it with `EARNINGS_URL` (`kit/program.jsx:120`), and read `cashOutOpen` (section 41), the only cash-out state the record holds; while it is null, say only where to look.
2. **Find its state in the Worker record.** Everything about the worker's day lives in one record (section 41). Name the fields the feature reads or writes and add them to the fixtures in `kit/worker-data.jsx`, never to a screen's local state, so no navigation can lose them (P1). One thing sits outside the record today: the Notifications inbox keeps its items as fixtures in `screens/notifications.jsx` (section 76 lists the gap). A feature that raises a new event adds its row there, its line to section 54 and its kind in section 60, and two code edits: the kind's `[glyph, tone]` in `ICON` (`screens/notifications.jsx:39-44`; a kind missing there falls back to `ICON_OTHER`, a neutral info glyph), and, if its row opens a new target, that target's row in section 32's route table plus the opts its screen needs. `open()` (`screens/notifications.jsx:111-118`) passes no opts except `{state: 'waiting'}` for `chat` and `rowTarget()` for `run`, so a target that needs a state gets its own branch there.
3. **Place it.** Pick the level from the navigation model in section 32: a tab, a pushed screen with Back, a sheet or a dialog. Give a screen an id in section 32's route table (opts, level, lit tab, Back) and handle that id in the host router that holds `{tab, stacks}`; screens only emit `onNavigate(id, opts)`. Check section 55 if it is a setting and section 54 if it has to reach a partner who is away.
4. **Compose it from the kit.** Use parts from Components, Shell, Chat, Worker and Credits. Each part's section lists its props, variants and states. Reach for a token, never a raw value. Add a kit part only when nothing fits (step 8).
   - Wrap a whole screen in `V2Screens.ScreenFrame`, the one frame for every signed-in screen (core, account and system states). Props (`screens/home.jsx:4-13`): `ScreenFrame {worker, tab, loading, compact, landmark, overlays, onNavigate, frame, openMenu, scrollTo, status, statusLabel, credits, nav, offlineBanner, onReconnect, className, children}`. Pass `tab` for the lit tab by the rule in section 32 (a top-bar door keeps the tab you came from), `worker` for the top bar's run chip and credits (`status`, `statusLabel` and `credits` override them, null hides), `onNavigate(id, opts)` for every chrome event, and `frame={false}` to drop the chrome inside a guide specimen (children and overlays come back alone). The screen's Dialog and Sheet go in `overlays`, never in `children`: AppFrame mounts them in its overlay layer over the whole window (`.v2-frame-overlays`, inset 0, `kit/shell.jsx:31`), so the scrim covers the top bar and the nav as well as the content. `nav={false}` drops the bottom nav; `offlineBanner={false}` drops the pinned offline Banner when the screen says it itself (Home), and `onReconnect` is that Banner's Try again; `scrollTo` moves the content band to a `[data-section]`; `openMenu` forces a top-bar menu open (guide); `loading` blanks the run chip, the credits, the Activity badge and the offline Banner while the record loads (`screens/home.jsx:138-147`); `compact` and `landmark` pass to AppFrame.
   - If the screen confirms its changes with a toast, wrap it in `V2Screens.ToastScope` and call `useScreenToast().show()`; AppFrame draws the window's one live region, so every toast is announced.
5. **Write the copy.** Use the glossary in section 70: Always ask and Automatic, AI credits, Sign in and Sign out, job and run. Say the consequence before the choice (P3). Mark every new string Proposed until the PM approves it. No em dash.
6. **Cover every state.** Loading (50), empty, error and offline (51), confirm or undo (52), consent (53). Then the floor: visible focus, labels on icon buttons, 4.5:1 text, 32px targets, reduced motion.
7. **Add it to the guide.** A section file in `guide/sections/`, its entry in `guide/catalog.jsx`, a partial in `design-md/`, a script line in `index.html`, and a ref in `guide/refs/` for every V2 value or string it quotes.
   - The partial and the guide section each carry the part's prose and spec values, and nothing builds one from the other (`tools/build-design-md.js` reads only `design-md/`), so write and change them in the same edit and check one against the other.
   - Write the section with the guide's blocks (`Section`, `Part`, `StateGrid`, `CompareRow`, `SpecDrawer`, `register`), documented with a worked example in the header comment of `guide/kit-guide.jsx`.
   - Write refs in the format in `guide/refs/README.md` (id, file, line, needle, value), in the slice's own `guide/refs/<feature>.js` (one file per slice, never another slice's), loaded from `index.html`.
   - Names follow the catalog's contract (`guide/catalog.jsx:4-6`): the section file is `guide/sections/<group>-<id>.jsx` and calls `V2Guide.register('<id>', Component)`; the partial is `design-md/<number>-<id>.md` and starts with `## <number> <title>`.
   - Numbering: a section number is a stable id that other sections and the PM cite ("section 54"), and the groups use every number from 00 to 77 with no gaps (`guide/catalog.jsx:10-21`), so never renumber. A new section takes the last number of its group plus a letter (a new screen after 69 is `69a`, partial `design-md/69a-<id>.md`, heading `## 69a <title>`); a new Meta section takes the next number after 77. Put its entry at that place in the catalog's `sections` array (array order is the guide's and DESIGN.md's order) and widen the group's `numbers` range ("57-69a").
   - A new kit part or screen also gets a row in the catalog's `kit` or `screens` array (name, file, stylesheet, status), which ds-check reads to prove it is on `window.V2Kit` or `window.V2Screens`.
8. **If it needs a new kit part.** One IIFE file `kit/<name>.jsx` that does `Object.assign(window.V2Kit, { Part })`, reads other parts lazily at render, `v2-` classes in a kit stylesheet, hover, focus, active, disabled, loading and error in CSS, tokens only, 300 lines at most.
9. **Run the checks.** `node tools/ds-check.js` to 0 errors and `node tools/build-design-md.js`. Then look at it in the guide by eye: the checks read files, not pixels.
10. **Merge into V2.** V2 here is a port of the PM's own source, so merge there. Load `tokens.css`, `kit/base.css`, `kit/motion.css`, the kit stylesheets you use and the screen stylesheets the screen uses (`screens/core.css` for the skeletons and core screens, `screens/account.css` for the settings-group column), then the kit scripts after React and Babel, then `screens/home.jsx` (ScreenFrame, ToastScope, ListSkeleton, LoadError and HomeSkeleton, the helpers step 4 uses) and every other screens file that holds a helper the screen reads: `screens/settings.jsx` (CONFIRM_COPY, useConfirmStep, ConfirmDialog, pendingBody), `screens/activity.jsx` (rowTarget, ledgerRows), `screens/help.jsx` (ReportProblemSheet, reportAbout), `screens/welcome.jsx` (Welcome, TermsSheet), `screens/connected-apps.jsx` (ConnectedAppRows) and `screens/system-states.jsx` (SystemStates). Screens read these at render and draw nothing, with no error, when one is missing: without `screens/settings.jsx`, Account's Sign out opens no dialog (`screens/account.jsx:109`). AppFrame holds the window's one toast region, so screens need no host of their own beyond ToastScope. Use the V2 today look until the switch (section 00, Two looks): link `tokens-v2-today.css` right after `tokens.css` and set `data-v2-look="today"` on V2's `html` element, so the screen matches the V2 around it. Build the screen with `window.V2Kit` parts, delete the V2 code the matching recommendation in section 73 names, and keep V2's URL states working (section 72) so review links still open the right state.
11. **Close the loop.** Once it ships in V2, change the part's status to In V2, move its row out of Recommendations, and add a line to the changelog (section 77).

### Worked example: Pause daily runs

How section 62's pause row was built, step by step, so each step can be checked against a part that exists. Proposed copy throughout, as in section 62.

- **Job:** keep the partner in control (P4: every promise has a control). V2 promises "You can pause, stop, or disconnect anytime." (`blueai/worker_flow.jsx:67`) and has no control for it (R05).
- **State:** the record's `paused` field (null, or {until}), section 41. The WorkerCard, the top bar status chip and Settings all read it; `numbers()` gives the cost (`toGo`, `daysLeft`).
- **Place:** a row in Settings > Worker (section 62), a pushed screen; the change applies at once (section 55).
- **Parts:** `ListRow` "Daily runs" with a `Switch`. Turning it off opens a `Dialog` (task variant, md): the `Select` "Pause until" first, then the cost for the date picked (role=status); turning it on resumes at once. A `Toast` confirms each change, with no Undo: the dialog already asked, and turning the switch back on is the way back (section 52, rule 1, for anything that "can cost today's day or future days": "say the cost before the choice, and ask once", and "No Undo: a day cannot be given back by a toast.").
- **Copy:** section 62 owns every string; the example only shows where each sits. The dialog title is the question ("Pause daily runs?"); the Select says until when, first; then the cost in days for the date picked, from `numbers()` (role=status), before the buttons; the actions are Keep running and Pause (danger: it loses days, section 52); a toast says what changed ("Daily runs paused.", "Daily runs are back on."); the row says until when and what it costs while paused.
- **States:** running daily (the switch on, the next run time); pause dialog open (the switch busy while it decides); paused until a date (the row says until when and what it costs); resumed.
- **Checks:** the switch is role=switch named "Daily runs"; dialog focus moves in and returns to the switch; the cost is in the dialog body, read before the buttons; ds-check to 0.

### Do / Don't

- **Do:** start from the Worker record and the job the feature serves; use a kit part as it is and pass props; say what a choice costs before the partner makes it; run ds-check before handing anything over.
- **Don't:** keep the worker's state inside a screen; restyle a kit part in the screen with inline colours; invent a synonym for a glossary word; edit DESIGN.md by hand (edit the partial and rebuild).
